# TypeScript construct fixture

Test repository for the Swamp PR-analysis behaviors:
`pr-diff` → `pr-checkout` → `ts-definitions` → `change-matcher` → `ts-details` → `change-report`.

- `main` is the base. Each PR is one branch off `main` with one commit, named `pr/<ID>-<slug>`.
- Each PR gets `expected/<ID>/` with the resource each behavior should write:
  `changedLines.json` (pr-diff), `changedComponents.json` (change-matcher), `details.json` (ts-details, where listed).
- `ts-definitions` is tested on `main` alone: one expected definitions list per base file.
- Expected files are written by hand from the rules below — never generated by running the pipeline.
  New-error expectations come from `tsc` on the PR branch (independent instrument).

## Toolchain and base state

- TypeScript **7.0.2**, pinned as a root `devDependency` (`node_modules/.bin/tsc` after install).
- npm workspace: root `package.json` declares `"workspaces": ["packages/*"]`; `package-lock.json` is committed.
  Install with `npm ci --ignore-scripts` (no install scripts run). The root declares `typescript`; `packages/web` declares the React packages and the
  workspace package `@fixture/shared`.
- Four TypeScript projects, each with its own `tsconfig.json`:
  `.` (root: `src`, `test`, `js`; `"types": []`, `"resolveJsonModule": true`, excludes `packages`), `legacy` (CommonJS), `packages/web` (React,
  `"jsx": "react-jsx"`, path alias `@/*` → `./src/*`), `packages/shared` (`@fixture/shared`, imported by `packages/web`).
- Base compiles with **zero errors** in all three: `tsc -p .`, `tsc -p legacy`, `tsc -p packages/web` (measured 2026-10-30).
- `.gitattributes` keeps `src/crlf.ts` and `src/bom.ts` byte-exact (`-text`); without it the CRLF/BOM cases stop testing anything.
- PR edits are stored as data in `prs/*.json` (`id`, `title`, `file`, `old`, `new`; `old` must occur exactly once).
  `python3 tools/measure_prs.py . node_modules/.bin/tsc prs/<set>.json` applies each edit in place, compiles all three
  projects, restores the file, and prints the new errors; it cross-checks parsed errors against the raw count and
  asserts the base is clean before and after.
- `tools/check_pr.py` compiles the checked-out tree and compares (1) the errors with the recorded line for `pr/<ID>`
  in `prs/measured-errors.txt` and (2) each project's compiled files with `prs/compiled-files.json` (the base set plus
  the PR's recorded additions and removals); any other ref must have zero errors and exactly the base set. It prints
  the compiled-file counts with every verdict, so a shrunken compile scope fails instead of passing vacuously.
  CI (`.github/workflows/fixture-errors.yml`) runs it on each PR's exact head commit and on pushes to `main`, reading
  the answer key from `origin/main` (`FIXTURE_ANSWER_REF`) so a PR cannot change its own expected result.
  Record scope with `python3 tools/measure_prs.py . node_modules/.bin/tsc --scope-out prs/compiled-files.json prs/*.json`.

## Documentation convention (code-level)

| File type | Convention | Why |
|---|---|---|
| `.ts` / `.tsx` | **TSDoc** `/** … */`, no type braces: summary, `@remarks`, `@param name - text`, `@returns`, `@throws`, `@example`, `@typeParam T - text`, `@deprecated`, `@internal`, `@defaultValue`, `{@link X}` | Types are already in the code; braces would duplicate them and can go stale |
| `.js` | **JSDoc with types**: `@param {T} name`, `@returns {T}`, `@type`, `@typedef`, `@callback` | In JavaScript these tags *are* the type information |
| any | `//` inside bodies for the "why"; `//` directly above a declaration counts as its doc | Agents read and trust comments |

Measured with TypeScript 7.0.2 (`node.jsDoc`, `getJSDocTags`, `getTextOfJSDocComment` from `typescript/unstable/ast/jsdoc`):

- `/** */` attaches to its declaration: all 15 documented declarations in `src/documented.ts` — classes, class properties, methods, getters, functions, interfaces, interface members, enums, enum members, type aliases.
- `//` above a declaration is **not** attached — `ts-definitions` must collect it from the text.
- `@param` tags expose the parameter name (`JSDocParameterTag`, `name`).
- `@typeParam` is parsed as a generic tag with no name field — read the type-parameter name from the tag text.
- In `.js`, `@typedef` and `@callback` produce `JSTypeAliasDeclaration` nodes; `@type` attaches to the variable statement.
- With `strict` + `checkJs`, an undocumented `.js` parameter is error TS7006; a file marked `// @ts-nocheck` gives callers no checking at all (`scale("a", {})` compiles).
- A JSDoc type change in `.js` breaks TypeScript callers (S9, S10).

## Classification rules

`ts-definitions` records per definition: `codeHash` (tokens without comments/whitespace; in `.js` includes JSDoc type tags),
`commentHash` (comments inside the body), `docHash` (doc directly above), `docKind` (`block` | `line` | `none`),
`docTags` (parsed tags: name, parameter name, type text, text), `typedTags` (any `{…}` type braces), `text`, `parts[]`.

| # | Rule |
|---|---|
| 1 | Doc above changed → `docChanged`. In `.js`, a type-tag change → `signatureChanged`. |
| 2 | Whitespace only → **cosmetic**. Comment inside the body changed → `commentChanged` (not cosmetic). |
| 3 | Reordered within a file → **moved (same file)**, with old and new line ranges. |
| 4 | Object-literal members → own components in container (e.g. `api`). |
| 5 | Callbacks passed to calls at file top level, or inside another callback component → own components, kind `callback`, named `callee("first string arg")`; nested labels form the path (`describe("Cart") › it("adds")`). No string arg → positional name (`get#2`), flagged positional. Callbacks inside ordinary function bodies (including inline JSX handlers) stay part of the function. A call whose result is assigned to a declared variable is rule 10, not rule 5. |
| 6 | Nested functions — declared with `function` **or** bound to a local name (`const handleAdd = () => {…}`) — and classes declared in functions → own components, container `[outer]`. |
| 7 | Top-level and member variables → components. Local variables that are **not** functions → not components. |
| 8 | Overloads and merged declarations → one component; each part (overload signature, declaration block) recorded with its own lines. |
| 9 | Class with a changed member → "modified via members" plus the member. |
| 10 | Wrapped definitions `const X = wrapper(fn)` (`memo`, `forwardRef`, `lazy`, HOCs, non-React `withAuth(…)`) → component named `X`, kind from the inner function, `wrappers: [...]` outermost first. Wrapper added/removed → `modifiersChanged`. |
| 11 | Hook callbacks inside a component (`useEffect`, `useLayoutEffect`, `useMemo`, `useCallback`, `useImperativeHandle`) → part of the component, labelled in the construct path (`CartView › useEffect#1`, numbered in source order) with the dependency-list text recorded. Deps-only change → `effectDepsChanged`. |
| 12 | Top-level expando assignments: `X.Y = function …` → component `Y` in container `[X]` (`Tabs.Panel`); `X.prop = value` → property `prop` of `X` (`Badge.displayName`). |
| 13 | Arrow or function expressions in class fields (`increment = () => {…}`) → kind `method`, `field: true`. |
| 14 | React kinds: a function, arrow or class that returns JSX or extends `Component` → kind `component`; a function named `use` + capital letter → kind `hook`; `createContext(…)` at top level → kind `context`; the result of `memo`, `forwardRef` or `lazy` → kind `component`. A `"use client"` / `"use server"` directive added or removed → file-level `directiveChanged`. |
| 15 | Top-level executable statements (IIFEs, loops, `createRoot(…).render(…)`, other expression statements that are not rule-5 callbacks or rule-12 assignments) → **file-level** items, labelled by their label (`outer:`) or callee, else by position; not components. |

Definitions used by the expectations:

- **Own code vs. members.** A container (class, interface, enum, namespace, object literal, component or function with nested components) is compared on its *own* code — its text with every child component's span removed. If only children changed, the container is reported `modified` with `viaMembers`.
- **Parameter properties are class properties.** `constructor(public owner?: string)` declares `Cart.owner`; removing the parameter deletes that property.
- **Flags.** `signatureChanged`, `bodyChanged` (functions, methods, accessors, constructors); `typeChanged` (type aliases, interface members, JSDoc `@typedef`); `valueChanged` (variables, properties, enum members); `modifiersChanged` (async, static, abstract, readonly, decorators, `private`, wrappers); `exportChanged`; `commentChanged`; `docChanged`; `deprecationChanged`; `visibilityIntentChanged`; `docStale`; `docMaybeStale`; `undocumented`; `docStyleMismatch`; `effectDepsChanged`; `viaMembers`; `fileRenamed`; `nonLiteralLabel`; `parseErrors`; `weakTypes` (JavaScript without type information).
- **Change values.** `added`, `deleted`, `modified`, `renamed` (same body, new name), `moved` (same code, new file), `movedSameFile` (rule 3), `cosmetic` (whitespace only).

Clarifications (each closes an ambiguity found by cross-checking the answer key against an independent extraction):

- **What a declaration's doc is (rule 1).** The comment block or blocks immediately above it with no blank line in between. A block separated by a blank line — such as a standalone JSDoc `@typedef` — is not that declaration's doc, even though TypeScript attaches it to the next declaration (`node.jsDoc`). Example: changing the `@typedef` in `js/plain.js` does not change `label`'s doc (B46, S9).
- **Rule 10 applies only when the variable holds a function**: the callee is a plain identifier (`memo`, `forwardRef`, `lazy`, `withRetry`, a higher-order component) and an argument is an inline function. `values.reduce((a, b) => a + b, 0)` or `items.map(…)` are not wrapped definitions.
- **Hook calls follow rule 11**: `const add = useCallback(fn, deps)` and `const total = useMemo(fn, deps)` inside a component *or hook* are part of the enclosing component or hook — not rule 6 or rule 10 components.
- **A container's own code ignores whitespace and member separators** (commas, semicolons, line breaks), and **a member's leading comments belong to the member**. Adding, removing or re-documenting a member alone makes the container `viaMembers`.
- **Renamed or moved containers carry their members**: members follow the container and are not reported separately unless they changed themselves (R03: `CartPanel › handleAdd` is not reported).
- **Export lists count**: adding `get` to `export { routes, get }` makes `get` `modified` with `exportChanged`, although its declaration text is unchanged (A16).
- **`export *` propagates**: adding, removing, renaming or changing an exported declaration in a module re-exported with `export * from` changes the re-exporting module's public API; optimal output says so (A04, A05, A06, A07, A12, S3).
- **Inferred exported types are impact**: a change can alter the exported type of an unchanged declaration elsewhere (A13: `viaNamespace` in `src/consumers.ts` becomes `Promise<number>`); optimal output reports it.
- **Parse errors degrade the file**: with a syntax error, the parser's recovery can restructure every later declaration (D06: later functions nest inside `plain`); optimal output marks the file degraded instead of reporting the resulting adds and deletes.
- **Exported import aliases are components**: `export import InnerAlias = Geo.Inner` is a component of kind `alias`; a non-exported `import X = Ns.Y` is a file-level import (E14).
- **A member moved to another container in the same file is `moved`**, with the container change in `detail` (K05: static `create` from `Animal` to `Container`).
- **A change of declaration form is `modifiersChanged`**, with the form in `detail`: function declaration ↔ `const` arrow function (K06), class component ↔ function component (K07).
- **CommonJS**: `require(…)` bindings, including destructuring, are file-level imports, not variable components; `module.exports = { … }` and `exports.x = …` are the export list, so adding or removing a name there is `exportChanged` on that declaration (J12, J13).
- **Indentation and line endings lie outside a single-line declaration's text**: a single-line declaration or member whose line only changed indentation or line ending is unchanged, not cosmetic; multi-line ones are cosmetic (G15, G16).
- **References cross workspace packages only from the consumer's project**: references to `formatPrice` queried from `packages/shared` find only its declaration; from `packages/web` they include `Price.tsx:9` (measured, W01). A pipeline must query every workspace project.
- **Compare with the PR's own base**: a stacked PR (base: another PR's branch) or a stale PR (cut from an older `main`) is judged on its diff from its merge base, never from the current tip of `main` (G01, G04, G05).
- **Multi-commit PRs are judged on their net change**; intermediate commits, including a change and its revert, are not part of the expected output (G02, G03).

`change-matcher` order of checks (one component can carry several flags):

1. `codeHash` differs → code modified; split into `signatureChanged` / `bodyChanged`.
2. `commentHash` differs → `commentChanged`.
3. `docHash` differs → `docChanged`; from `docTags` also:
   `deprecationChanged` (`@deprecated` added/removed), `visibilityIntentChanged` (`@internal` added/removed).
4. Definite doc checks (any change to the component): **`docStale`** when `@param` names ≠ parameter names or `@typeParam` names ≠ type parameters.
5. Hints: `docMaybeStale` (code changed, doc exists, `docHash` unchanged); `undocumented` (exported, `docKind: none`);
   `docStyleMismatch` (`.ts` with `typedTags`).
6. No hash differs but text does → **cosmetic**.
7. Same key, different position in the same file → **moved (same file)**.

## Evaluating output against a PR

For anyone judging a pipeline's output against a PR description (the same content as that PR's entry in
`prs/expect.json`). The description is the answer key. Descriptions are never edited: corrections and additions are
posted as PR comments and recorded in `prs/expect.json` on `main`, which is the current answer key — read the PR's
comments too.

| Item in the description | How to judge |
|---|---|
| **Changed components** | **Required.** Each row must be found, identified by file + container path + name. A missing row is a miss. |
| Change (`added`, `modified`, …) | **Required** to match exactly. |
| Flags | **Required**: every listed flag. An extra flag is a deviation only if the rules above say it cannot apply. |
| Kind | **Required: the noun** (function, method, class, interface, type, enum, enum member, namespace, variable, property, accessor, constructor, static block, call signature, method signature, callback, component, hook, context, object). Words in parentheses and adjectives (`arrow`, `async`, `generic`, `merged`, `abstract`, `generator`, `FC`, `field`, …) describe the form and are **not** required. |
| Detail | Expected content, judged on meaning, not wording. |
| **Must not be reported as changed** | **False-positive check.** Reporting any of these as changed is an error. |
| Other components not listed | Judge against the classification rules; reporting an unchanged component as changed is a false positive. |
| **File-level changes** | **Required.** |
| Compiler errors | **Measured facts.** If the pipeline reports diagnostics, its new errors must equal this list (file, line, code). |
| References | **Measured on the base.** A pipeline that reports references must include these; TypeScript may return more (for example the whole interface-member family, see S7). |
| Public API (`publicApi` in `prs/expect.json`) | **Measured.** If the pipeline reports public-API or exported-type changes, they must agree with these declaration changes, including changes to unchanged files (A13). |
| Notes | Expected detail, **except** where a note says reporting is optional — those are bonus. |
| Summary an agent should receive | Judged on meaning: it must state the same facts (what changed, the construct, the effect, the breakage), not the same words. |

Suggested scores per PR: identification (required components and file-level items found), classification (change and flags correct), precision (no false positives, including the must-not list), semantics (errors and references), summary.
